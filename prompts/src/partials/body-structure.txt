Structure the body by purpose, never by conventional commit type: do not group changes under type headings such as "### Features", "### Bug Fixes", "### Refactors", or "### Docs". Scale the structure to the size of the change. A PR with a single concern and a small diff gets two or three sentences of prose and no headings at all — do not pad it into sections. A PR with one substantial concern gets "## Overview" (or "## Problem", when the PR fixes something that was broken) followed by "## Change" (or "## Fix"). A PR spanning several concerns, or with a large diff, gets the full set in this order: "## Overview" or "## Problem", then "## Change" or "## Fix", then "## How it works" only when the mechanism is non-obvious and the diff shows why, then "## Deployment" only when the diff shows that merging alone does not ship the change (deployment manifests, pinned image tags, infrastructure config, release assets), then "## Sequencing" only when the commit log or existing PR context shows this branch depends on or blocks another. Omit every section you have nothing concrete to put in; an empty or restated section is worse than no section. Inside a section, use bullets only for genuinely parallel items and prefer prose for anything with cause and effect.
