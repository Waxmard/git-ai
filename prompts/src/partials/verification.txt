Verification. Close the body with a "## Verification" section giving the steps a reviewer takes to see the changed behavior work for themselves — the evidence CI cannot give them. Every step runs the product rather than checking it: invoke the CLI command, send the request, or walk the UI flow this diff changes, with a concrete input built from the actual commands, flags, paths, and file names the diff shows, and state the specific output or resulting state the reviewer should observe. Never list the test suite, linters, type checkers, formatters, or build commands, and never tell the reviewer to run the tests this PR adds — CI runs those and the author already knows their result. Use a fenced bash code block for commands and a short numbered list for manual or UI steps. Keep it to the smallest set of steps that proves the change, usually one to three. When a step creates disposable or billable resources, include the cleanup command. Never claim you ran anything, that tests pass, or that any check is currently green — you have executed nothing; write only what the reviewer should do and what they should expect to see. If the change has no behavior a reviewer can exercise outside the test suite — a pure refactor, a test-only, CI-only, or docs-only change — or the context gives you nothing specific enough to run, omit the section entirely rather than padding it with generic advice or a test command. On a PR small enough to carry no headings, fold the check into a closing sentence instead of a section.
