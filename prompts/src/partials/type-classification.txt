feat > fix > perf > refactor > test > build > ci > docs > style > chore; only use test, build, ci, docs, style, or chore when the PR contains no feat, fix, perf, or refactor change. First frame the repo's user POV — who consumes what this repo produces and what they perceive as its output — and judge each change by its impact on that audience; "user-facing" is defined by that POV, so the same change can take different types in different repos, and a <repo_guidance> block stating the POV is authoritative. Classify each change by its role, not its file format or path: prompt, template, schema, query, and config files are functional code, but that applies to config that defines behavior, not to the values it pins — bumping a version, model id, dependency, or other pinned value without changing the behavior surface is chore, never feat; a script or helper that only runs inside the build, CI, or release pipeline is build or ci, never feat; documentation or generated files touched alongside real code or tests never make the PR docs or chore. Never add ! to the title automatically. Independently of the title type, inspect <diff> for compatibility changes; commit subjects and <draft> can omit them. Check removed or renamed documented commands, agent or plugin names, config keys, environment variables, public API arguments, and machine-readable output fields. A replacement with similar functionality does not preserve compatibility unless the old interface still works (for example, through an alias). Internal helper changes and additive optional fields alone are not breaking changes. If the supplied context suggests this PR might remove or incompatibly change behavior that users of the current release rely on — e.g. a removed command or flag, renamed required argument, or changed output format that consumers parse — explain the old interface, its replacement or removal, and the affected usage in one concrete sentence, then append this exact standalone blockquote to the body:
> **Possible breaking change:** Confirm compatibility before merge. If breaking, add `!` before the title's colon (for example, `feat!:`).
Omit the note only when context establishes that the changed interface was introduced after the last tag and was never shipped, or that compatibility is preserved. A version tag alone does not establish when an interface shipped; if a concrete interface change is visible but its release history is unknown, retain the possible-breaking note. Preserve an existing note instead of adding a duplicate.
