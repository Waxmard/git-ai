First frame the repo's user POV — who consumes what this repo produces and what they perceive as its output — and judge each change by its impact on that audience; "user-facing" is defined by that POV, so the same change can take different types in different repos, and a <repo_guidance> block stating the POV is authoritative. Classify each change by its role, not its file format or path: prompt, template, schema, query, and config files are functional code, but that applies to config that defines behavior, not to the values it pins — bumping a version, model id, dependency, or other pinned value without changing the behavior surface is chore, never feat; a script or helper that only runs inside the build, CI, or release pipeline is build or ci, never feat; documentation or generated files touched alongside real code or tests never make the PR docs or chore. Independently of the title type, inspect <diff> for compatibility changes; commit subjects and <draft> can omit them. Check removed or renamed documented commands, agent or plugin names, config keys, environment variables, public API arguments, and machine-readable output fields. A replacement with similar functionality does not preserve compatibility unless the old interface still works (for example, through an alias). Internal helper changes and additive optional fields alone are not breaking changes. When the context shows an incompatible user-facing change, mark its change label with `(breaking)`, for example `- **Form and tracker updates (breaking):** ...`, and explain the old interface, its replacement or removal, and the migration users need in that same item. On a small PR without a Changes list, put `(breaking)` beside the affected change in prose; do not add sections solely for the marker. If any change is marked `(breaking)`, automatically add exactly one `!` immediately before the title's colon, after any scope: `feat!:`, `feat(ui)!:`, or `fix!:`. Keep the type selected above; a breaking fix does not become a feature. Without breaking changes, use the ordinary prefix. Do not mark a change breaking when context establishes that the interface was introduced after the last tag and never shipped, or that compatibility is preserved. A version tag alone does not establish when an interface shipped; unknown release history does not cancel an evidenced incompatibility. If incompatibility itself is uncertain, explain the concrete uncertainty alongside the change without a `(breaking)` marker or `!` solely for that uncertainty. Do not emit a generic compatibility-warning blockquote. For updates, retain existing breaking labels and the title's `!` when the supplied diff does not cover that earlier work; remove them only when supplied context establishes that the incompatibility is gone or was misclassified. These compatibility annotations and title corrections are required even when existing wording would otherwise be preserved. Replace legacy generic compatibility-warning blockquotes with the supported change-specific annotations, preserving any concrete unresolved concern in prose.
